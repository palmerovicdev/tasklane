01

Arquitectura general

Cuatro capas con dependencias en una sola dirección y un flujo de datos unidireccional: la UI envía comandos hacia abajo y recibe snapshots inmutables hacia arriba. El contenedor de servicios de la plataforma hace de inyector de dependencias; no se introduce ningún framework de DI.

ui · actions TasklaneToolWindowFactoryStateTabPanelQuickAddPopupTaskEditorPopupTasklaneConfigurableAnAction ×12
↓ comandos tipados↑ StateFlow<Snapshot>
application TaskServiceConfigServiceRepositoryRegistrySearchServiceExportServiceNotifier
↓ lectura/escritura↑ DTO + migraciones
data TaskFileStoreAttachmentStoreMigrationRunnerTasklaneSettings (PSC)StorageLayout
↓ tipos puros↑ sin dependencias
domain TaskTaskStateTaskPriorityLinkExtractorDateGrouperTriggerParserTaskExporter

La capa domain no importa nada de com.intellij. Es la única que se testea con JUnit puro, sin BasePlatformTestCase, y ahí vive toda la lógica no trivial: triggers, agrupación por fecha, extracción de enlaces, exportación, ordenación.

Reglas de dependencia

  • La UI nunca toca data. No hay ninguna referencia a TaskFileStore fuera de service/.
  • Los componentes Swing no contienen lógica de negocio: un renderer decide cómo se pinta una fila, nunca qué estado tiene una tarea.
  • Ninguna clase del core referencia git4idea. El acceso a Git va detrás de la interfaz RepositoryProvider y su implementación se registra sólo si el plugin Git está presente.

Flujo unidireccional

// application/TaskService.kt
@Service(Service.Level.PROJECT)
class TaskService(private val project: Project, private val scope: CoroutineScope) {

    private val _snapshot = MutableStateFlow(TasklaneSnapshot.EMPTY)
    val snapshot: StateFlow<TasklaneSnapshot> = _snapshot.asStateFlow()

    private val dirty = MutableSharedFlow<RepoKey>(extraBufferCapacity = 64)

    init {
        scope.launch(Dispatchers.IO) {
            dirty.debounce(500.milliseconds)
                 .collect { key -> store.write(key, _snapshot.value.tasksOf(key)) }
        }
    }

    fun apply(command: TaskCommand) {                // único punto de mutación
        val next = reducer.reduce(_snapshot.value, command)
        _snapshot.value = next
        dirty.tryEmit(command.repo)
    }
}
Por qué StateFlow y no MessageBus

Un Topic obliga a cada consumidor a gestionar su suscripción con Disposer y a reconstruir estado a partir de eventos incrementales — la fuente clásica de UI desincronizada y de listeners filtrados al cerrar proyectos. Con un snapshot inmutable la UI siempre repinta desde la verdad completa y la cancelación la hace el CoroutineScope del servicio. Se reserva MessageBus para lo que la plataforma ya publica (eventos VCS, cambios de tema).

Coste aceptado

Repintar desde el snapshot completo es más caro que aplicar un delta. Con el modelo de árbol asíncrono y unos miles de nodos es irrelevante; si alguna vez deja de serlo, el reducer ya devuelve qué TaskId cambiaron y se puede pasar a actualización parcial sin tocar la UI.

Modelo de dominio

Inmutable, con identificadores estables y un hueco explícito para extensiones futuras. Los nombres son mutables; los IDs no. Esa separación es lo que permite renombrar un estado sin tocar una sola tarea.

Decisiones del modelo

  • body como texto plano, no como árbol de nodos. La búsqueda, la exportación y el diff en Git son triviales; el enriquecimiento (enlaces, imágenes) se deriva y se cachea en links / attachments para que pintar una fila nunca implique re-parsear.
  • Dos colores por prioridad. Un único RGB obliga a derivar la variante oscura por heurística y produce contrastes malos en Darcula. Con colorLight + colorDark se construye un JBColor que el IDE resuelve solo al cambiar de tema.
  • order disperso. Reordenar por drag & drop inserta en el punto medio ((a+b)/2) sin reescribir la lista entera; se renormaliza sólo cuando el hueco se agota.
  • extra como bolsa de compatibilidad. Al leer un fichero escrito por una versión más nueva, los atributos desconocidos se conservan ahí y se vuelven a escribir. Sin esto, abrir el proyecto con una versión vieja del plugin borra silenciosamente datos futuros.
  • completedAt es un hecho, no un derivado. Se fija la primera vez que la tarea entra en un estado terminal. Si el usuario la saca de Done y la vuelve a meter, se conserva la marca original salvo que se reabra explícitamente — es lo que hace que la agrupación histórica sea estable.

Corregido durante la Fase 1 · no hay capa de DTOs

El diseño original tenía un paquete data/dto con clases anotadas para com.intellij.util.xmlb. Al implementarlo apareció un problema que lo invalida: xmlb descarta los atributos que no reconoce. Eso destruye justo la garantía que Task.extra existe para dar — que abrir el proyecto con una versión vieja del plugin no borre datos escritos por una nueva.

La sustitución es TasksCodec, que mapea Element ↔ Task a mano sobre JDOM: todo atributo desconocido entra en extra y se vuelve a escribir tal cual. De paso desaparece la fricción de xmlb con Kotlin, que exigía DTOs con var y constructor sin argumentos. Hay un test que fija el comportamiento.

Persistencia

El requisito pedía analizar las opciones antes de elegir. Aquí está el análisis y la elección, que no es única: hay dos tipos de datos con necesidades distintas.

Las cuatro opciones

OpciónQué daQué falla aquí
PersistentStateComponentEscritura atómica, guardado fuera del EDT, roaming, recarga ante cambios externosLos @Storage son estáticos: no hay un fichero por repositorio sin StateSplitterEx, que es API semi-interna. Y los adjuntos necesitan un directorio propio de todas formas.
Ficheros dentro del repositorioLos datos viajan con el clon; versionables si el usuario quiereEnsucia repos ajenos y obliga a tocar sus .gitignore
.idea/ del proyecto abiertoUbicación canónica de datos por proyecto; sobrevive a «Invalidate Caches»; no se indexaCon varios repos, vive en la raíz, no dentro de cada subrepo
ProjectUtil.getProjectCachePathFuera de VCS por definición, sin ensuciar nadaEs el directorio de caches. Aquí hay contenido escrito por el usuario que no puede morir al limpiar caches
Elección · tres niveles

Configuración del proyecto (estados, prioridades, triggers, agrupación por estado) → PersistentStateComponent de proyecto, @Storage("tasklane.xml"), que la plataforma escribe en .idea/tasklane.xml. Queda fuera del directorio auto-ignorado a propósito: un equipo puede versionarla y compartir el flujo de trabajo.

Plantilla de defaults → PersistentStateComponent de aplicación, SettingsCategory.TOOLS. Lo único que roamea. Siembra los proyectos que aún no tienen configuración.

Estado de UI (repo seleccionado, tab activa, filtros, nodos expandidos) → PersistentStateComponent a nivel proyecto con StoragePathMacros.WORKSPACE_FILE. Es por proyecto y por máquina, y workspace.xml ya está fuera de VCS.

Tareas y adjuntos → almacén propio, un directorio por repositorio bajo .idea/tasklane/, escrito con java.nio y serializado con xmlb.

Disposición en disco

├── tasklane.xml                       # config del proyecto: estados, prioridades, triggers
│                                      #   versionable — el equipo comparte el flujo
└── tasklane/                          # datos locales, auto-ignorados

    └── repos/

La separación es deliberada: la configuración es compartible, los datos son locales. tasklane.xml lo gestiona PersistentStateComponent y vive fuera del directorio auto-ignorado, así que un equipo puede versionar sus estados y prioridades sin arrastrar los TODOs personales de nadie. El .gitignore con * dentro de nuestro propio directorio mantiene los datos fuera de VCS sin tocar ni una línea del .gitignore del usuario.

Formato

<tasks version="1" repoKey="sinonte-backend-api-a3f91d0e">
  <task id="7c2f…" state="s-todo" priority="p-high" order="3000"
        createdAt="1757635200000" updatedAt="1757638800000">
    <body>Revisar https://youtrack.jetbrains.com/issue/ABC-123
![](tasklane:9f86d08188…e7cf)</body>
  </task>
</tasks>

XML y no JSON por una razón concreta: empaquetar kotlinx-serialization en un plugin provoca conflictos de classloader con la copia que trae la plataforma, un fallo que aparece en runtime y sólo en algunas versiones del IDE. JDOM ya está en la plataforma y no añade nada. Además .idea es un mundo XML: el formato queda consistente con sus vecinos.

El mapeo lo hace TasksCodec a mano, no XmlSerializer. La razón es concreta: xmlb descarta los atributos que no conoce, y eso vacía de contenido la promesa de extra. Mapeando a mano, un atributo escrito por una versión futura se lee, se guarda y se vuelve a escribir intacto.

Escritura segura

  1. Serializar en memoria, en Dispatchers.IO.
  2. Copiar el tasks.xml actual a tasks.xml.bak.
  3. Escribir tasks.xml.tmp y forzar FileChannel.force(true).
  4. Files.move(tmp, target, ATOMIC_MOVE, REPLACE_EXISTING).

Un Mutex por RepoKey garantiza un único escritor. Si el disco está lleno o faltan permisos, el fallo ocurre en el paso 3 y el fichero bueno sobrevive intacto. Las escrituras van por debounce(500 ms), más un flush síncrono en ProjectCloseListener.projectClosing — síncrono a propósito, porque el CoroutineScope del servicio ya está cancelado en ese punto.

Lectura y recuperación

  • Carga perezosa por repositorio; el repo activo se precarga en un ProjectActivity, fuera del EDT.
  • Fallo de parseo → se renombra a tasks.corrupt-<timestamp>.xml, se intenta .bak, y sólo si tampoco se arranca vacío — siempre con una notificación que enlaza al fichero. Nunca en silencio.
  • version mayor que la soportada → el repositorio se abre en solo lectura con un aviso, en lugar de degradar el fichero. Es la contrapartida de extra: entre los dos, una versión vieja del plugin no destruye datos de una nueva.
  • Migraciones como cadena de Migration que opera sobre el Element de JDOM antes de mapear a dominio.
Alternativa contemplada · guardar dentro de cada repo

Se deja como ajuste opcional («Store task data inside each repository» → <repoRoot>/.tasklane/) para quien quiera que los TODOs viajen con el clon o compartirlos con el equipo. No es el valor por defecto porque escribir en repos que el usuario no pidió tocar es intrusivo.

Estados como tabs

Cada estado es un Content del ContentManager de la tool window, no isCloseable. Da la barra de tabs nativa, la navegación con Alt+←/→ del keymap y la opción «Show tabs in one row» sin escribir nada. Un JBTabbedPane interno se descartó porque no se integra con el header ni con el keymap.

Con más de cinco o seis estados la fila de tabs se aprieta en una tool window lateral. Por eso el ajuste «Vista: tabs · lista única con secciones» reutiliza exactamente el mismo componente de árbol y presenta los estados como nodos raíz. Reordenar o renombrar estados reconstruye las tabs preservando la selección por StateId, nunca por índice.

El árbol

CheckboxTree con la raíz oculta y dos tipos de nodo: GroupNode (grupo de fecha) y TaskNode.

Corregido durante la Fase 1 · sin AsyncTreeModel

El diseño original combinaba CheckboxTree con StructureTreeModel/AsyncTreeModel. No componen: CheckboxTree castea su modelo a DefaultTreeModel para notificar cambios de nodo y trabaja sobre CheckedTreeNode, mientras que AsyncTreeModel opera con descriptores de estructura.

Se conserva CheckboxTree, que era la razón de la elección — hit-testing del checkbox y toggle con Espacio ya resueltos — y se mantiene el EDT libre por otra vía: el trabajo caro (filtrar, ordenar, agrupar) se hace fuera del EDT y en el hilo de UI sólo queda construir los nodos y recargar. Si con decenas de miles de tareas eso llegara a notarse, la salida es Tree + AsyncTreeModel con hit-testing propio, que ya estaba presupuestado como riesgo.

  • Por qué árbol y no JBList: la agrupación por fecha necesita secciones plegables, y el árbol trae gratis TreeSpeedSearch, navegación por teclado, TreeState para recordar qué estaba expandido y selección múltiple.
  • Por qué CheckboxTree: ya resuelve el hit-testing del checkbox y el toggle con Espacio, que es literalmente el requisito «completar con un clic». Su renderer base es un JPanel con JCheckBox + ColoredTreeCellRenderer, justo la composición que hace falta. Se desactiva la propagación a hijos con la CheckPolicy.
  • Por qué AsyncTreeModel: construir el modelo con miles de nodos ocurre fuera del EDT. Es la diferencia entre una tool window que se siente ligera y una que congela el IDE al cambiar de repo.

La fila

Renderer propio de dos líneas — tree.rowHeight = 0 habilita altura variable por fila. De izquierda a derecha: franja de prioridad de 3 px pintada con JBColor(colorLight, colorDark), checkbox, texto (primera línea del cuerpo, con elipsis), y fecha alineada a la derecha vía appendTextPadding de SimpleColoredComponent. Segunda línea, sólo si hay algo que mostrar: tags, indicador de enlaces y de imágenes.

La prioridad es una propiedad visual de la fila, no un eje de navegación: no hay secciones «HIGH / MEDIUM / LOW». Por debajo de unos 220 px de ancho el renderer retira la columna de fecha y luego la segunda línea, de modo que el título siempre se lee.

Barra de herramientas

ActionToolbar construida desde un ActionGroup declarado en plugin.xml, con targetComponent apuntando al árbol para que las acciones reciban el contexto correcto. Contiene: nueva tarea, selector de repositorio (ComboBoxAction con speed search), toggle de agrupación por fecha, filtros de prioridad y estado, exportar, expandir/colapsar y acceso a los ajustes. El campo de búsqueda (SearchTextField, con historial persistido) va sobre el árbol.

El menú contextual del árbol es un ActionGroup registrado, así que todas sus entradas aparecen en Settings → Keymap y en Search Everywhere sin trabajo extra.

Triggers de prioridad en vivo

Un DocumentListener pasa el texto por TriggerParser en cada pulsación. Si el prefijo coincide, el chip de prioridad cambia de color al instante y el trigger se consume: lo que se guarda es "Resolver fallo de autenticación en Android", no "!!! Resolver…". Si el usuario borra el trigger, la prioridad vuelve a la anterior.

La resolución es por coincidencia más larga primero sobre el primer token, y exige un espacio detrás. Así !!! gana a !, y un texto como !importante revisar no dispara nada.

Valores por defecto sensatos

El proyecto propuesto no es «el último usado» sino el repositorio del fichero abierto en el editor (FileEditorManager.selectedTextEditor → repositorio que contiene ese fichero), con el último seleccionado en la tool window como respaldo. Es el detalle que hace que crear una tarea desde el fichero en el que estás trabajando no requiera tocar el selector.

VcsRepositoryManager.VCS_REPOSITORY_MAPPING_UPDATED   → recalcular
ProjectLevelVcsManager.VCS_CONFIGURATION_CHANGED      → recalcular
GitRepository.GIT_REPO_CHANGE                         → refrescar rama en el tooltip

VCS_REPOSITORY_MAPPING_UPDATED es el evento correcto, no GIT_REPO_CHANGE: se dispara cuando cambian los mappings y las instancias de repositorio ya están creadas. Al abrir el proyecto, GitRepositoryManager puede devolver una lista vacía durante los primeros milisegundos — por eso el primer render usa la última lista conocida de layout.xml y se corrige con el primer evento, sin parpadeo.

Git como dependencia opcional

<depends optional="true" config-file="tasklane-git.xml">Git4Idea</depends>

El plugin funciona sin Git: sin él, ContentRootProvider produce un pseudo-repositorio «Project». Ninguna clase del core importa git4idea, porque hacerlo provoca NoClassDefFoundError en IDEs donde el plugin Git esté desactivado.

Profundidad y comportamiento del selector

El requisito habla de repos en subdirectorios hijos directos de la raíz. Se implementa como un filtro de profundidad configurable (por defecto 1), pero con una salvedad: un repositorio más profundo que ya tenga tareas nunca se oculta — aparece bajo un separador «Other» en el selector. Filtrar datos existentes fuera de la vista es indistinguible de perderlos.

Búsqueda

No hace falta un índice invertido

5.000 tareas de ~200 caracteres son ~1 MB de texto normalizado. Un contains sobre cadenas ya normalizadas y cacheadas cuesta del orden de 1–3 ms; 50.000 tareas siguen por debajo de 20 ms. Eso cabe holgadamente dentro de un solo tick de debounce y ocurre fuera del EDT. Construir un índice invertido aquí sería infraestructura sin beneficio medible, y añadiría invalidación incremental — la parte que se rompe.

Diseño

  • Documento cacheado por tarea: texto en minúsculas y sin diacríticos (Normalizer.NFD + descarte de marcas), de modo que autenticación encuentre autenticacion. Se invalida al escribir esa tarea, no en cada búsqueda.
  • Consulta: texto libre más operadores state:, p:, repo:, is:done|open, has:link|image, #tag.
  • Emparejado y ranking: NameUtil.buildMatcher(...) → MinusculeMatcher, con matchingDegree() para ordenar. Es el mismo motor que usa Search Everywhere, así que el comportamiento le resulta familiar al usuario.
  • Resaltado: SpeedSearchUtil.appendColoredFragmentForMatcher en el renderer — subrayado nativo, correcto en ambos temas, sin pintar nada a mano.
  • Ejecución: MutableStateFlow<String> → debounce(120 ms) → flatMapLatest en Dispatchers.Default, que cancela la búsqueda anterior. Los resultados se publican como StateFlow y el modelo del árbol filtra sobre ellos.
  • Alcance: repositorio actual por defecto, con toggle «Buscar en todos los repositorios».
interface TaskSearchIndex {
    fun search(query: TaskQuery, scope: SearchScope): List<ScoredTask>
    fun invalidate(ids: Collection<TaskId>)
}
// Implementación inicial: LinearScanIndex
// Si el profiling alguna vez lo pide: InvertedTrigramIndex, sin tocar la UI

La interfaz existe precisamente para que la decisión de arriba sea reversible sin coste.

Enlaces e imágenes

Enlaces

La extracción ocurre al escribir, no al pintar: LinkExtractor recorre el cuerpo (URLs sueltas, www. y [texto](url), ignorando bloques de código) y el resultado se cachea en task.links. Pintar una fila nunca implica ejecutar una regex.

En el árbol, los fragmentos de enlace se pintan con SimpleTextAttributes.LINK_ATTRIBUTES — el estilo de enlace de la plataforma, correcto en cualquier tema — y el clic se resuelve con SimpleColoredComponent.findFragmentAt(x). El cursor cambia a mano al pasar por encima.

El acortado antepone el dominio: https://youtrack.jetbrains.com/issue/ABC-123 se muestra como youtrack.jetbrains.com/…/ABC-123 y, si aún no cabe, como youtrack.jetbrains.com/…. La URL completa vive en el modelo y en el tooltip; lo que se abre es siempre la original.

Indicador de enlaces en la fila: un icono de cadena con el número, en la segunda línea. Un clic abre el enlace si sólo hay uno; si hay varios, un ListPopup con las URLs acortadas. Funciona esté donde esté el enlace dentro del texto, y nunca hace falta entrar a editar. Sólo se abren esquemas http y https vía BrowserUtil.browse: un file: o un javascript: pegado en una tarea no debe ser clicable.

Imágenes

Representación elegida

Cuerpo en Markdown-lite, imágenes como blobs direccionados por contenido fuera del fichero de tareas. La referencia es ![](tasklane:<sha256>) y el fichero vive en attachments/<sha256>.png.

Direccionar por contenido resuelve tres cosas de golpe: la misma captura pegada en dos tareas ocupa un blob, no hay nombres que colisionen, y la recolección de basura es contar referencias. Base64 embebido se descartó por lo obvio — infla el fichero de tareas, lo carga entero en memoria y destroza cualquier diff.

Markdown se elige porque mantiene el cuerpo como texto plano (búsqueda, exportación y diff triviales) y porque coincide con la ruta de renderizado que recomienda JetBrains: convertir con org.jetbrains:markdown y mostrar en JBHtmlPane. Pero no se impone como sintaxis al usuario: quien escriba texto plano nunca ve una marca.

Editor de tareas

  • Componente: EditorTextField — un editor real de IntelliJ, con undo, selección múltiple y el keymap del usuario. Con el plugin Markdown presente (dependencia opcional) se obtiene resaltado de sintaxis; sin él, texto plano.
  • Pegar: un TransferHandler sobre el componente del editor comprueba DataFlavor.imageFlavor, normaliza la imagen en Dispatchers.IO (reescalado si supera el máximo configurado, re-codificación a PNG) e inserta la referencia en la posición del cursor dentro de un WriteCommandAction, para que ⌘Z funcione.
  • Previsualización en línea: InlayModel.addBlockElement con un EditorCustomElementRenderer que pinta la imagen escalada bajo la línea de la referencia. Los inlays se recalculan con debounce al cambiar el documento y la BufferedImage escalada se cachea; JBUIScale mantiene la nitidez en HiDPI.
  • Ampliar: el clic sobre el inlay abre el fichero adjunto con FileEditorManager, que lo entrega al plugin Images incluido en el IDE — zoom, ajuste y rueda del ratón, gratis. Respaldo: un JBPopup con la imagen escalada.
  • Borrar: el cursor sobre el inlay y Supr, o la acción de contexto «Quitar imagen».
  • Recolección: AttachmentGc corre al abrir el proyecto, fuera del EDT, y borra blobs sin referencias con un periodo de gracia — para que deshacer un pegado no deje una referencia rota.

Se descartó incrustar el preview JCEF del plugin Markdown: viola la restricción de no usar WebView y añade una dependencia dura a un plugin que no está en todos los IDEs.

10

Estados y prioridades configurables

Ambos viven en TasklaneConfig, un PersistentStateComponent de proyecto que la plataforma escribe en .idea/tasklane.xml, como listas ordenadas de entidades con UUID estable. Renombrar cambia name; el id no se toca nunca. Esa es toda la razón por la que renombrar un estado no puede perder tareas.

Por proyecto, sin el coste de serlo

Configuración por proyecto permite flujos distintos por cliente y deja que un equipo versione .idea/tasklane.xml para compartir estados y prioridades. Su único coste real —reconfigurar cada proyecto nuevo— se neutraliza con una plantilla de defaults a nivel aplicación: un proyecto sin configuración se siembra desde ella al abrirse, y los ajustes ofrecen «Guardar como plantilla para proyectos nuevos». La plantilla es lo único que roamea.

La semilla de fábrica es ToDo · Doing · Done, con Done marcado como terminal y agrupado por completedAt, y Low · Normal · High con los triggers !, !! y !!!.

Borrado con reasignación obligatoria

┌ Delete state "Doing" ────────────────────────┐
│                                              │
│  42 tasks use this state.                    │
│  Move them to:  [ ToDo            ▾ ]        │
│                                              │
│                      [ Cancel ]  [ Delete ]  │
└──────────────────────────────────────────────┘

Un DialogWrapper sin opción destructiva por defecto. Cancelar no borra nada. Si es el último estado, el borrado se bloquea — siempre debe quedar al menos uno. Lo mismo para prioridades.

Resiliencia ante configuración desincronizada

Con la configuración por proyecto, un tasks.xml que referencia un stateId inexistente deja de ser el camino común — pero no desaparece: basta con que alguien edite .idea/tasklane.xml en una rama, resuelva mal un merge, o copie datos entre proyectos. La red de seguridad se mantiene:

  • La tarea no se descarta: se remapea al estado por defecto.
  • El ID original se guarda en extra["origStateId"], así que si la configuración vuelve, se puede restaurar.
  • Una notificación informa de cuántas tareas se remapearon, con acción para revisarlas.

Triggers

  • Resolución por coincidencia más larga sobre el primer token, con espacio obligatorio detrás.
  • Unicidad validada en vivo en los ajustes; un duplicado se marca con aviso en línea antes de poder guardar.
  • Son opcionales por prioridad, y el sistema completo se puede desactivar.
  • Funcionan con prioridades añadidas por el usuario sin ningún caso especial: el parser sólo conoce la lista ordenada por longitud.

Agrupación por fecha, por estado

Cada estado tiene su propia Grouping y su propio DateAnchor. Done agrupa por completedAt; ToDo no agrupa; otro estado podría agrupar por createdAt. Los grupos son Today, Yesterday, This week, luego Sep 10 dentro del año en curso y Sep 2025 más atrás, todo con DateFormatUtil para respetar el locale.

Página de ajustes

BoundSearchableConfigurable con Kotlin UI DSL v2 y dos tablas envueltas en ToolbarDecorator (añadir, quitar, subir, bajar). La columna de color usa ColorPanel, con celdas separadas para claro y oscuro. Los atajos no se configuran aquí: hay un enlace a Settings → Keymap filtrado por el grupo de acciones del plugin, porque duplicar el sistema de keymap sería exactamente lo que el requisito prohíbe.

Edge cases

Estados y prioridades

  • Borrar el último estado o la última prioridad: bloqueado.
  • Borrar uno con tareas: diálogo de reasignación obligatorio; cancelar no borra nada.
  • Reordenar estados con la tool window abierta: las tabs se reconstruyen preservando la selección por StateId, no por índice.
  • stateId o priorityId desconocido al cargar: remapeo al valor por defecto, ID original preservado en extra, notificación con recuento.
  • Dos triggers idénticos: validación en vivo impide guardar.
  • Trigger que es prefijo de otro (! vs !!!): gana el más largo.
  • Marcar como terminal un estado que ya tiene tareas: se ofrece una vez rellenar completedAt desde updatedAt.
  • Quitar el flag terminal: completedAt se conserva; no se destruye información.

Repositorios

  • Repositorio añadido o eliminado en caliente: el selector reacciona por evento, sin reiniciar.
  • Repositorio que desaparece del disco con tareas dentro: entrada deshabilitada, datos intactos.
  • Dos carpetas con el mismo nombre en rutas distintas: el hash de ruta en RepoKey las separa.
  • Repositorio movido o renombrado: cambia el RepoKey; los datos huérfanos quedan y hay una acción de reasignación en ajustes.
  • Submódulos Git: aparecen como repositorios independientes, bajo «Other» si exceden la profundidad configurada.
  • Plugin Git desactivado: pseudo-repositorio «Project», sin errores.

Persistencia

  • tasks.xml corrupto: .bak, y si falla, vacío con notificación. El fichero malo se conserva renombrado.
  • Fichero escrito por una versión futura: solo lectura con aviso, nunca degradado.
  • Dos ventanas del IDE sobre el mismo proyecto: se comprueba lastModified antes de escribir; si cambió, se recarga y se fusiona por taskId con last-write-wins según updatedAt.
  • Disco lleno o sin permisos: falla la escritura temporal, el fichero bueno sobrevive, notificación de error.
  • Cierre del IDE con el debounce pendiente: flush síncrono en projectClosing.

UI

  • Tool window por debajo de ~220 px: el renderer retira fecha y segunda línea antes que truncar el título.
  • Miles de tareas en un estado: modelo construido fuera del EDT; grupos anteriores a «Yesterday» colapsados por defecto.
  • Cambio de tema en caliente: colores vía JBColor, repintado por LafManagerListener.
  • Escalado al 200 %: todas las medidas del renderer y de los inlays pasan por JBUI.scale.
  • Tarea vacía: Quick Add deshabilita Enter.
  • Texto pegado de megabytes: se acepta, pero la fila usa sólo la primera línea y el renderer corta a un máximo de caracteres.

Enlaces e imágenes

  • Esquema no http(s): no clicable.
  • URL dentro de un bloque de código: no se extrae.
  • Adjunto referenciado pero ausente: marcador de posición en el inlay; la referencia no se borra.
  • Misma imagen en dos tareas: un solo blob; sólo se recoge cuando no queda ninguna referencia.
  • Captura enorme del portapapeles: se reescala al máximo configurado antes de guardar.
  • Deshacer tras pegar: el texto se revierte; el blob queda huérfano y lo recoge el GC tras el periodo de gracia.

Plan de implementación

Ocho fases, cada una entregable y probable a mano. El orden se desvía del propuesto en dos puntos, por dependencias reales: multi-repo va antes que Quick Add, porque el popup necesita el selector de proyecto; y la exportación sube a la fase de enlaces, porque sólo depende del dominio y sale casi gratis ahí.

Versionado · una fase, una versión media

Cerrar una fase sube la versión media: la fase N deja el plugin en 0.N.0, y la 1.0.0 queda reservada para cuando estén las ocho. El número de versión y el de fase son el mismo número, así que pluginVersion en gradle.properties dice por sí solo hasta dónde llega el plugin instalado.

La versión baja (patch) queda para lo que no mueve el plan: correcciones, compatibilidad con una plataforma nueva, retoques de texto. La 0.1.0 es la única excepción retroactiva — cubrió a la vez el andamiaje de la Fase 0 y el núcleo de la Fase 1, que no llegaron a publicarse por separado.

Riesgos y decisiones abiertas

Riesgos técnicos

Conflicto de atajos en macOS

Los dos atajos propuestos ya están ocupados en el keymap de macOS: ⌘⌥R es Resume Program y ⌘K es Commit. La mitigación es doble: registrar ambas acciones en plugin.xml (para que sean configurables en Keymap) y además instalarlas sobre el panel con registerCustomShortcutSet, leyendo el atajo desde el keymap. Así ganan dentro de la tool window sin pelear con el binding global. ⌘K queda resuelto así. ⌘⌥R es global y sí compite de verdad con Resume Program; la decisión tomada es mantenerlo como default — el IDE avisa del conflicto en Settings → Keymap y el usuario elige cuál gana. Se documenta en el README y en la descripción del plugin.

Resuelto en la Fase 1 · serialización

Este riesgo se materializó y se resolvió eliminando xmlb del camino de datos: ver la corrección en §03 y §04. El dominio quedó inmutable y sin capa de DTOs.

Filas de dos líneas en CheckboxTree

Altura variable por fila (rowHeight = 0) más el hit-testing del checkbox heredado. Hay que verificar pronto que el checkbox sigue respondiendo con la fila alta; si no, se reimplementa el hit-testing sobre Tree, que es media jornada de trabajo conocido. La Fase 1 usa filas de una línea, así que sigue abierto.

Nota de implementación: la franja de prioridad se pinta como Border del renderer, no como componente. El BorderLayout del renderer de CheckboxTree ya tiene el checkbox en el WEST, así que insertar un componente ahí sería frágil; pintando en el borde la franja queda en el extremo izquierdo real de la fila.

Inlays de imagen y rendimiento

Recalcular inlays en cada pulsación es caro. Debounce más caché de la BufferedImage escalada por (AttachmentId, ancho).

Dependencia opcional a Git4Idea

Cualquier referencia a git4idea desde una clase del core provoca NoClassDefFoundError donde el plugin Git esté desactivado. Se aísla en su propio descriptor (tasklane-git.xml) y se accede sólo por interfaz.
